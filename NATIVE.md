# Мост между Flutter и Rust-ядром

```
Flutter UI ──> AppController ──> Backend (интерфейс)
                                   ├─ CliBackend   запускает `cablesend --json`   (Windows / macOS / Linux)
                                   ├─ FfiBackend   dart:ffi → C ABI (src/ffi.rs)   (Android / iOS)
                                   └─ DemoBackend  выдуманные устройства           (если ядра нет)
```
Кодогенерация (`flutter_rust_bridge`) не нужна: интерфейс состоит из 8 функций на простых C-строках.

## C ABI (`src/ffi.rs`)
| Функция | Что делает |
|---|---|
| `cs_version()` | версия интерфейса (сейчас 1) |
| `cs_scan(beacon_port)` | ищет устройства; ответ придёт событием `scan` с полями `id`, `name`, `platform`, `addr`, `via` |
| `cs_receive_start(dir, name, port, beacon_port)` | начать приём; вернёт порт, `-1` уже запущен, `-2` порт занят |
| `cs_receive_stop()` | остановить приём |
| `cs_answer(1/0)` | принять / отклонить ожидающее предложение |
| `cs_send(to, name, files)` | отправить; `files` — пути через `\n`; вернётся сразу |
| `cs_next_event()` / `cs_free_string(p)` | забрать следующее JSON-событие (NULL — пусто) и освободить строку |

Никаких обратных вызовов: Dart раз в 100 мс забирает события (`FfiBackend._drain`). Все долгие операции идут в потоках ядра, UI не блокируется.

Ядро само знает свой идентификатор устройства и выбрасывает собственный маяк из результатов
поиска, поэтому мосту не нужно отфильтровывать себя по имени. На настольных ОС `receive` и
`peers` — **разные процессы**, поэтому оболочка передаёт им один и тот же `--id`
(`CliBackend._instanceId`); без этого компьютер нашёл бы сам себя.

Входящие соединения ядро обрабатывает строго по одному, поэтому ожидающее предложение всегда
одно и `cs_answer` не нуждается в идентификаторе передачи.

## Сборка
**Android**: порядок такой.
1. `cd app && flutter create --platforms=android,... .`
2. `tools/build_android.sh` (нужны NDK и `cargo install cargo-ndk`): кладёт `libcablesend.so` в `jniLibs/<abi>/`.
3. `tools/apply_android.sh`: добавляет в проект разрешения, foreground-сервис `ReceiveService` и `MainActivity` с каналом `cablesend/service`. Скрипт можно запускать повторно.

Что делает сервис: пока включён «Принимать файлы», держит процесс живым при свёрнутом приложении, показывает уведомление и держит MulticastLock (нужен для приёма UDP-маяка на части телефонов). Когда приходит предложение файлов, текст уведомления меняется на «… хочет отправить N файлов. Откройте приложение». Принять файлы можно только в открытом приложении; если не ответить 90 секунд, предложение отклоняется.
Ограничения: на Android 15 сервис типа `dataSync` система останавливает примерно через 6 часов; на Android 13+ нужно разрешить уведомления (приложение спросит само, но без разрешения сервис всё равно работает).
Файлы по умолчанию сохраняются в папку приложения (`getExternalStorageDirectory`), разрешения на память не нужны.

**iOS** (`tools/build_ios.sh`, только на Mac): создаёт `CableSendCore.xcframework`. Дальше в Xcode:
1. Перетащите xcframework в Runner → *Frameworks, Libraries* → «Do Not Embed».
2. Build Settings → *Other Linker Flags*: `-force_load $(PROJECT_DIR)/CableSendCore.xcframework/ios-arm64/libcablesend.a` (для симулятора путь другой).
3. Build Settings → *Strip Style* = «Non-Global Symbols» (иначе символы `cs_*` вырежут и `DynamicLibrary.process()` их не найдёт).
4. `Info.plist`: `NSLocalNetworkUsageDescription` (обязательно, иначе iOS молча блокирует локальную сеть).

## Как это работает с кабелем на телефоне
Телефон слушает порт 53317 (приём) и умеет отправлять на адрес.
- **ПК → Android**: ПК делает `adb forward` на порт телефона (это уже в `cablesend send --adb`).
- **Android → ПК**: на ПК запускают `cablesend receive --adb-reverse`. Это пробрасывает порт **53320 на телефоне** к ПК. Приложение само ищет этот туннель при сканировании и показывает «Компьютер по USB» (вид связи `CableKind.usbHost`).

Порты: **53317** — приём файлов, **53318** — UDP-маяк, **53320** — туннель «телефон → ПК».
- **ПК → iPhone**: через usbmuxd (`cablesend send --ios`), приложение должно быть открыто.
- **iPhone → ПК по одному USB-кабелю** сейчас невозможно: iOS не умеет сам открыть соединение к ПК. Варианты: режим модема по USB (тогда это обычный IP) или добавить «забор» файла ПК-стороной (на будущее).
- Сетевые кабели и USB-Ethernet адаптеры работают как на ПК: обнаружение по UDP-маяку.

## Проверено / не проверено
- Проверено: все 9 тестов ядра (`cargo test`), в том числе на самообнаружение, дубликаты
  устройств и безопасность временного файла. C ABI из Python (`ctypes`): приём, подтверждение, отказ, ошибка соединения, мгновенный перезапуск, два одновременных поиска, 20 МБ с проверкой хеша, молчаливая обработка «проб». Скрипт `apply_android.sh` проверен на макете проекта (манифест остаётся корректным XML, повторный запуск ничего не дублирует).
- **Не проверено**: сборка под Android/iOS, Kotlin-код сервиса, Dart-код (`ffi_backend.dart`, `foreground_service.dart`), работа туннеля `adb reverse` и usbmuxd на реальных телефонах.
